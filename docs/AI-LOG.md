## How I directed and checked the agent

| Practice | Example | What it changed |
|---|---|---|
| **Make it lay out options before building**: weighted comparisons, with the weights set by me against the brief | Stack, architecture, broker, API style and data access ([DECISIONS.md](DECISIONS.md)) | Every decision has recorded alternatives; I overruled its recommendation when I disagreed, choosing controllers over minimal APIs (#7) |
| **Turn load-bearing claims into experiments** | Its explanation of concurrent booking conflicts, tested with a real-Postgres race (#3) | The claim was incomplete; that result led to the benchmark and to the architecture |
| **Distrust numbers that look too good or too bad** | The first benchmark results (#4) | Three sources of bias found and removed before any number was published |
| **Gate each step on a build and tests against real infrastructure** | Layer-by-layer build with Testcontainers Postgres and Kafka (#6, #7, #13) | A test written for the controllers conversion caught validation errors under the wrong field names |
| **Run the whole system, not just the tests** | Docker Compose runs of every scenario (#8, #9) | Found seed-data bugs no test executed; showed no double-booking under bursts and failover |
| **Find the cause before accepting a rerun** | A test that failed once and passed again (#10) | Traced to cold start; fixed with a startup warm-up (2.45 s → 0.26 s) instead of a retry |
| **Read the output, not the summary** | The tracing dashboard and the demo scripts (#11, #12) | Removed trace noise; caught a failover demo that reported success without a failover |
